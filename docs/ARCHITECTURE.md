# Архитектура tradebot-core

Подробное описание устройства ядра (v0.1–v0.4). Команды установки и
запуска — в [README](../README.md).

**Стек:** ассемблер x86-64 (точечно, с C-fallback) · C11 (ядро) · C++20
(обвязка JSON поверх вендоренного rapidjson) · Linux (epoll, eventfd).

**Платформа:** Linux x86-64 (сборка и тесты выполняются на других
архитектурах в портативном режиме — asm-пути отключаются автоматически).

---

## Быстрый старт

```bash
# Одна команда: зависимости (локально в .deps/, без root) + сборка + тесты
./setup.sh

# Основной путь — CMake (то же руками)
cmake -B build -DCMAKE_BUILD_TYPE=RelWithDebInfo
cmake --build build -j
ctest --test-dir build --output-on-failure     # 20 тестов

# Запасной путь — чистый Makefile
make && make test

# С printf-маркерами диагностики во всей библиотеке
make markers

# Демо ядра v0.1: симулятор опроса источников (15 секунд)
./build/bot_demo --duration 15000 --ledger ./tradebot_events.jsonl --seed 42

# Демо реестра событий: живой конвейер с загрузкой/выгрузкой шагов (30 секунд)
./build/events_demo --duration 30000 --ledger ./events_demo.jsonl 2>markers.log

# Демо механизма торговли: 11 ордеров, все ветви исполнения (14 секунд)
./build/exec_demo --duration 14000 --ledger ./exec_demo.jsonl --seed 42

# Арбитраж: живые котировки mainnet, shadow-исполнение (25 секунд)
./build/arb_demo --duration 25000 --ledger ./arb_demo.jsonl

# Арбитраж офлайн: локальный mock-RPC со спредом, полный конвейер (8 секунд)
./build/arb_demo --replay --duration 8000 --ledger ./arb_demo.jsonl
```

Аргументы всех демо: `--duration МС`, `--ledger ПУТЬ`, `--seed N`
(по умолчанию — энтропия из RDTSC). Выход — `Ctrl+C`, журнал
закрывается штатно.

| Демо | Что показывает |
|---|---|
| `bot_demo` | опрос источников на симуляторе: ветки SUCCESS/ERROR/PENDING, 429+Retry-After, backoff+jitter, 401-стоп, circuit breaker, token-bucket, пул+цикл, Event Ledger с дедупликацией, глобальный обработчик ошибок |
| `events_demo` | живой конвейер шагов: загрузка/выгрузка на ходу, слежение за событиями, контекст блокировок, мосты к планировщику и журналу |
| `exec_demo` | механизм торговли: конвейер preflight→commit, атомарность слота (провал = откат), wrap/unwrap, PENDING-поллинг, retryable-повторы, slippage-защита, баланс-лист до/после |
| `arb_demo` | арбитражный конвейер: фильтры 1–4, Decision Engine (минимальная ставка до верха контракта), shadow-исполнение; `--replay` — офлайн на mock-RPC, `--live-exec` — из Safe (раздел 11) |

│   ├── runtime/  #   ratelimit, breaker

│   ├── ledger/   #   ledger
│   ├── exec/     #   codes, u256, route, wallet, backend, backend_dex,
│   │             #   safe_exec (живое исполнение из Safe), engine
│   ├── net/      #   http (транспорт net/replay)
│   ├── sign/     #   tx (ключ, RLP, EIP-1559)
│   ├── user/     #   arb (фильтры 1–4, Decision Engine, рантайм)

Библиотеки: `tb_core` (C11) и `tb_runtime` (C++20, зависит от tb_core).
Демо и тесты линкуются против них.

### Слои и языки

| Слой | Язык | Ответственность |
|---|---|---|
| `arch` | asm x86-64 + C | хот-споты с рантайм-диспетчем (cpuid) |
| `core`, `sched`, `runtime`, `ledger`, `exec` | C11 | всё управляющее ядро + механизм торговли (uint256, маршруты V3, кошелёк/слоты, конвейер исполнения) |
| `json` (Envelope) | C++20 + rapidjson | сериализация единого формата ответов |
| демо, тесты | C11 / C++ | пример и верификация |

Правило asm: **хот-спот + обязательный C-fallback с идентичной семантикой**.
Выбор пути — в рантайме, поэтому на платформе без SSE4.2 ядро просто
использует табличный CRC-32C (тест сверяет оба пути).

## 1. Обработчик ошибок — на всё приложение

`tb_error_t` — **POD-значение** (нулевое состояние = «нет ошибки»):
копируется присваиванием, не владеет кучей, безопасен к `{0}`-инициализации.
Контекст накапливается **текстовым следом** (`wrap`/`promote`), а не цепочкой
указателей.

```c
tb_error_t err = TB_ERROR_INIT;
if (tb_ledger_emit(led, "api.response", json, NULL, &id, &err) != 0) {
    tb_error_wrap(&err, TB_LOC, "provider=%s op=%s", src, op);
    tb_report(&err);            /* глобальный обработчик: счётчики + журнал */
}
```

- **Домены**: CORE / SCHED / NET / API / LEDGER / JSON / USER (USER — для
  фильтров 1–4 и движков будущих итераций).
- **Коды** — единая таксономия внутри домена; для API — стандартизация
  ответов источников: `RATE_LIMIT, TIMEOUT, NETWORK, SERVER, UNAUTHORIZED,
  NOT_FOUND, BAD_REQUEST, PARSE, PENDING, CIRCUIT_OPEN, …`
- Каждая ошибка несёт `severity`, `retryable`, `http_status`,
  `retry_after_ms` — ровно то, что нужно политикам повтора.
- **Глобальный обработчик** (`tb_set_error_handler`) — единая точка учёта и
  журналирования ошибок всего приложения; `TB_SEV_FATAL` доходит до
  panic-политики.

### Реестр кодов — «база данных обработчика»

`tb/core/error_registry` — каноническое место, где живут:

1. **метаданные унифицированных кодов** (имя, severity, retryable) —
   `tb_error_set()` подтягивает их автоматически;
2. **шаблоны отображения ответов источников**: `(источник, HTTP-статус,
   паттерн тела) -> унифицированный код` — `tb_registry_map_response()`
   с разрешением правил «точное по источнику → пользовательское → общее
   `*` → эвристика по классу статуса»;
3. расширение в рантайме: `tb_registry_add_source_map()` — подключение
   нового API сводится к добавлению правила.

Именно поэтому пятый модуль (и любые будущие) не решает заново, «что значит
ошибка 429 от GeckoTerminal» — он читает унифицированный код из реестра.

## 2. Планировщик задач

**Гибридная модель** (как согласовано): один поток-владелец выполняет все
callback'и; блокирующие операции (HTTP, fsync, архив) уходят в пул потоков,
завершение возвращается в цикл через `tb_loop_post()`.

- **event loop**: `epoll_wait` + `eventfd` (кросс-поточные постинги,
  сигнально-безопасная остановка по SIGINT);
- **таймерное колесо**: 2048 слотов × 8 мс (горизонт ~16.4 с) + overflow-куча
  для дальних дедлайнов с каскадом; чистая функция времени — детерминированно
  тестируется на виртуальных часах;
- **приоритетная очередь** (бинарная куча): `(приоритет, seq)`.

| Приоритет | Роль в боте |
|---|---|
| `CRITICAL` | предторговая проверка непосредственно перед сделкой |
| `HIGH` | завершения блокирующих операций, критичные обновления |
| `NORMAL` | регулярный опрос источников |
| `LOW` | discovery-сканирование, сбор статистики |
| `BACKGROUND` | исторические исследования, архивация |

```c
tb_loop_t *loop = tb_loop_create(2, &err);   /* 2 воркера пула */
tb_loop_call_every(loop, 900, TB_PRIO_LOW, "discovery", on_discovery, app, NULL);
tb_loop_post(loop, TB_PRIO_CRITICAL, "pretrade.check", on_check, ctx, free);
tb_loop_run(loop);                            /* текущий поток = владелец */
```

Контракты: планирование и отмена — из потока цикла (кросс-поточное — через
постинг); задачи-владельцы аргумента освобождают его через `dtor` ровно один
раз; отмена — атомарная пометка, физическое освобождение при выборке.

## 3. Модуль регистрации событий (`tb/events`)

Обработка события — это **конвейер зарегистрированных модулей**. Реестр
нужен всем — и ядру, и планировщику, и доменным модулям — как общий способ
собирать обработку из шагов **без переписывания цепочки**: добавить или
убрать шаг = `tb_evreg_add()` / `tb_evreg_remove()` в рантайме.

```c
tb_evreg_t *reg = tb_evreg_create(0, &err);

/* Цепочка собирается из шагов; порядок — порядок регистрации. */
tb_evreg_add(reg, "core",      core_fn,  NULL, NULL);
tb_evreg_add(reg, "ratelimit", tb_evmod_ratelimit_fn, &gate, NULL);
tb_evreg_add(reg, "breaker",   tb_evmod_breaker_fn,   &brk,  NULL);
tb_evreg_add(reg, "http",      http_fn,  &http_state, NULL);
tb_evreg_add(reg, "http_resp", resp_fn,  &http_state, NULL);

/* Вставка в середину и выгрузка — на ходу, остальные шаги не меняются. */
tb_evreg_add_before(reg, "http", "cache", cache_fn, &cache, NULL);
tb_evreg_remove(reg, "ratelimit", NULL);

/* Событие: создаётся, прогоняется, живёт в live-таблице. */
tb_event_t *ev = tb_event_create(reg, KIND_TVL, 0, NULL);
tb_evreg_dispatch(reg, ev, &err);          /* -> DONE/FAILED/BLOCKED */
```

### Две роли, два механизма

| Механизм | Что это | Примеры |
|---|---|---|
| **Модули (цепочка)** | шаги обработки события; загрузка/выгрузка шага | `core`, `ratelimit`, `breaker`, `http`, `http_resp`, кэш, будущие фильтры 1–4 |
| **Наблюдатели (подписки)** | реакция на переходы состояний | планировщик (`BLOCKED` → таймер на `wake_at`), Event Ledger (терминал → JSONL), метрики, кэш-хранитель |

Шаг возвращает действие: `TB_EV_ACT_CHAIN` (дальше), `TB_EV_ACT_DONE`
(успех), `TB_EV_ACT_FAIL` (ошибка — обязательно в событии), `TB_EV_ACT_BLOCK`
(ждать). Блокировка двух видов:

- `tb_event_block_until(wake_at)` — «шаг сделал работу и ждёт результата»
  (полёт запроса): продолжение **со следующего шага**;
- `tb_event_retry_at(wake_at)` — «событие должно пройти цепочку заново»
  (лимит, предохранитель, повтор после 429/5xx): на wake **шлюзы
  перепроверяются**, побочные шаги выполнятся заново.

### Слежение за живыми событиями

Live-таблица хранит `QUEUED / ACTIVE / BLOCKED` (+ терминальные до закрытия).
Каждое событие накапливает **текстовый след шагов** — «что принёс каждый
шаг» — и хранит ошибку **POD-значением** (`tb_error_t` без владения, копия
memcpy-безопасна — прямой выгрыш отказа от heap-цепочки `cause`):

```
  #30 kind=1 BLOCKED  попыток=4 шагов=8 wake=+1240ms blocked_by=breaker
      ошибка: [API/TB_API_RATE_LIMIT|HTTP 429|retry_after=1500ms|retryable] ...
      след:
        [core] проход 1: kind=YIELD_SCAN, цепочка из 5 шагов
        [ratelimit] granted: токен взят (granted=5, deferred=0)
        [breaker] allowed: CLOSED, сбоев подряд 0/3
        [http] GET YIELD_SCAN отправлен (полёт 25 мс, отправка №13)
        [http_resp] HTTP 429: Retry-After 1500 мс — повтор запроса
        повтор с начала цепочки: шлюзы перепроверяются
        ...
```

`tb_evreg_dump(reg, stdout)` — быстрая диагностика состояния целиком;
`tb_evreg_foreach/count` — программная инспекция по маске состояний.

### Контекст блокировок — без подразумеваемой арифметики

Урок теста breaker («открыт в t=2, охлаждение 100 → проба с t=102, а не
100») поднят до контракта: шаг-шлюз кладёт в след **сами величины**.
`tb_breaker_probe_at_ms()` возвращает `opened_at + cooldown` явно:

```
[breaker] rejected: OPEN с t=6760936, cooldown=3000 -> probe_at=6763936 (через 1240)
```

В HALF_OPEN с занятой пробой — короткая перепроверка (`проба занята`),
а не зависание с «ручным» wake.

### Интеграция с планировщиком и журналом

- **Мост к циклу** (демо `events_demo`): наблюдатель на `BLOCKED` ставит
  `tb_loop_call_later(wake_at)` → задача-продолжение вызывает
  `tb_evreg_continue()`. Планировщик ничего не знает про события, реестр —
  ничего про epoll: связка только через наблюдателя.
- **Мост к журналу** (`tb_ev_ledger_attach`): терминальные события пишутся
  в Event Ledger как `event.trace` (id реестра, kind, состояние, попытки,
  ошибка, весь след) и закрываются — live-таблица держит только живые.

### printf-маркеры диагностики

`tb/core/marker.h` — `TB_MARK(...)` в ключевых точках компонентов: в
release вырождается в `((void)0)`, включается определением
`TB_EVENT_MARKERS=1` (файл, `make markers`, опция CMake
`TB_ENABLE_MARKERS`). Демо `events_demo` собирается с маркерами всегда —
вывод в stderr: `[mark файл:строка] сообщение`.

```bash
./build/events_demo --duration 30000 --ledger ./events_demo.jsonl 2>markers.log
```

### Что нашла и починила эта итерация (спящие дефекты v0.1)

1. **`tb_task_table_remove` — неверный сдвиг-назад.** Условие переноса
   элемента при удалении из хеш-таблицы задач было перевёрнуто: элемент
   уезжал в дыру через свой «дом», цепочка пробирования рвалась,
   `reap_task` освобождал задачу при живом указателе в слоте →
   use-after-free при `tb_loop_destroy`. Проявлялся только на высокой
   каденции таймеров (демо реестра, ~2 тыс. задач). Исправлено по канону
   (Кнут, алгоритм R) + регрессионный стресс-тест в `test_loop`.
2. **Обрыв символов UTF-8 при усечении.** `vsnprintf` режет по байтам:
   сообщения ошибок и след шагов могли заканчиваться битой
   последовательностью — JSONL не проходил строгую валидацию. `tb_utf8_fit`
   (`core/strutil.h`) откатывает усечённые строки к последнему полному
   символу; маркер усечения следа `...` не дописывается повторно.

## 4. Политики повтора (каркас Universal API Runtime)

| Механизм | Реализация | Правило |
|---|---|---|
| Adaptive Backoff | `tb_backoff` | `delay = base << (attempt-1)`, потолок, защита от переполнения |
| Jitter | `tb_backoff` | равномерно в `[d·(1-f), d·(1+f)]` — разнос модулей во времени |
| **Retry-After** | `tb_backoff` | итог **никогда не меньше** разрешённого источником; jitter не даёт спросить раньше срока |
| Неретраебельные ошибки | `tb_backoff` | возврат 0 — повтор не планируется (401 ожиданием не исправить) |
| Rate Limiter | `tb_ratelimit` | token-bucket на источник (проектируемся консервативно: под 10 rpm, даже если источник допускает 30) |
| Circuit Breaker | `tb_breaker` | CLOSED→OPEN по порогу подряд идущих сбоев; OPEN→HALF_OPEN после охлаждения (`tb_breaker_probe_at_ms` — явный момент пробы); успех закрывает |

Шлюзы доступны и как **шаги цепочки событий** (`tb/events/builtins`):
`tb_evmod_ratelimit_fn` / `tb_evmod_breaker_fn` — те же политики, но
блокирующие события с полным контекстом в следе (токен через N мс;
opened_at / cooldown / probe_at).

Соответствие зафиксированной таблице решений:

| Требование | Компонент v0.1 |
|---|---|
| Единый формат API (JSON Envelope) | `tb/json/envelope` |
| SUCCESS / ERROR / PENDING | статусы конверта |
| Adaptive Backoff | `tb/sched/backoff` |
| Случайное распределение (Jitter) | `tb/sched/backoff` |
| Контроль лимитов (общий Scheduler) | `tb/runtime/ratelimit` + приоритеты цикла |
| Постоянные ошибки (Circuit Breaker) | `tb/runtime/breaker` |
| Приоритеты (Priority Queue) | `tb/sched/pqueue` + 5 уровней |
| Защита от дублей (Event Deduplication) | окно uuid-хешей в `tb/ledger` |
| Повторяющиеся данные (Cache) | roadmap (итерация 2) |
| Кросс-поточные completion'ы | пул потоков + `tb_loop_post` |

## 5. Event Ledger

Append-only JSONL-журнал — единая история проверок, решений и ошибок:

```json
{"event_id":8,"ts_ms":1793523252855,"ts":"2026-11-01T08:54:12.855Z",
 "type":"api.response","payload":{"schema_version":"1.0","source":"geckoterminal",
 "operation":"get_pool_ohlcv","status":"ERROR","request_id":2,
 "timestamp":1793523252855,"data":null,
 "error":{"code":"TB_API_RATE_LIMIT","domain":"API","severity":"WARN",
 "retryable":true,"http_status":429,"retry_after_ms":3000,"message":"..."},
 "retry":{"attempt":1,"next_attempt_at":1793523255855}}}
```

- `event_id` монотонный и **переживает перезапуск** (сканируется при open);
- опциональная **дедупликация по uuid** (окно 65536 хешей; переполнение —
  fail-open с предупреждением);
- режимы надёжности: `FLUSH_LINE` (строчная) и `FSYNC` (после каждой записи);
- тип `event.trace` — терминальные записи реестра событий (см. раздел 3):
  единая история получает и пошаговые следы конвейера.

## 6. API Response Envelope

Единый формат **всех** ответов источников — три статуса, строго типизированная
ошибка с каноническим именем кода из реестра, блок retry для ERROR/PENDING.
Roundtrip сериализация/разбор покрыт тестами; неизвестные коды и чужие схемы
отклоняются (`TB_JSON_SCHEMA`). Реализация — C++/rapidjson с чистым C-ABI:
C-ядро не видит C++ типов. Поле `retry_after` из HTTP-заголовка источника
переводится в `retry_after_ms` на границе адаптера.

## 8. Механизм торговли (Execution Engine)

v0.2 переносит на стек ядра семантику контракта-референса **MultiHopSwap**
(Solidity / Uniswap V3): не-кастодиальный помощник обмена с одно- и
многохоповыми маршрутами, нативным входом/выходом через wrap/unwrap и
жёсткими защитами (deadline, amountOutMinimum). Референс ценен именно
СЕМАНТИКОЙ — «что значит сделать своп», — а не кодом: у нас другой стек
и другие границы (нет EVM, «транзакция» — это прогон события по цепочке,
«роутер» — интерфейс бэкенда с симулятором сейчас и живым DEX-адаптером
в следующей итерации).

### Таблица переноса

| Контракт (Solidity) | Ядро (C11) |
|---|---|
| `swapExactInputSingle` / `swapExactInputMultihop` | `tb_exec_submit()` — один вход, маршрут из 1+ хопов |
| `encodePath(tokens, fees)` (pure) | `tb_route_encode()` / `tb_route_single()` |
| `_firstToken(path)` + `InvalidPath()` | `tb_route_first()` + валидация в `preflight` |
| `if (deadline < block.timestamp) revert` | шаг `preflight`: `TB_EXEC_DEADLINE_PAST` (+запас жизни бота) |
| `amountOutMinimum` (revert роутера) | сличение на бэкенде + инвариант в `settle`: `TB_EXEC_SLIPPAGE`; `0` → авто-минимум от политики |
| `msg.value != amountIn → WrongMsgValue()` | инвариант сведения дебета/кредита слота: `TB_EXEC_VALUE_MISMATCH` |
| `weth.deposit{value}` (на входе) | `tb_slot_wrap()` — и вход целиком уходит маршрутизатору |
| `weth.withdraw` + `call{value}` (на выходе) | `tb_slot_unwrap()` в `settle` (`TB_EXEC_SETTLE_FAILED` при сбое) |
| `receive() { if (msg.sender != weth) revert NotWeth() }` | инвариант: `tb_slot_credit(нативного)` запрещён — `TB_EXEC_NOT_WRAPPED` |
| `forceApprove(router, amountIn)` … `forceApprove(router, 0)` | журнал слота: approve → execute → сброс в 0 при расчёте |
| **атомарность одной транзакции** (revert откатывает всё) | **торговый слот**: commit применяется целиком, rollback отбрасывает всё |
| non-custodial, нет владельца/админа/rescue | движок не имеет привилегий над балансами: все мутации — через слот, в журнале |
| событие `Swapped(user, tokenIn, tokenOut, amountIn, amountOut)` | запись `trade.executed` в Event Ledger (конверт-схема) |
| `ISwapRouter` (внешний мир) | `tb_exec_backend_t` — vtable (симулятор сейчас, DEX-адаптер потом) |
| — (в EVM транзакция либо прошла, либо нет) | **PENDING**: `trade.submitted` + поллинг заполнения (202-семантика конвертов) |
| `uint256` | `tb_u256_t` — суммы в JSON десятичными строками |

### Конвейер исполнения

```
 ордер ──> │ preflight │──> │ ratelimit │──> │ breaker │──> │ quote │
           │ валидация │    │ токен-бакет│   │ предохра-│    │ожидаемый│
           │ deadline  │    │ бюджета   │    │ нитель  │    │ выход и │
           │ маршрут   │    │ бэкенда   │    │ бэкенда │    │ минимум │
           │ лимиты    │    └───────────┘    └─────────┘    └────────┘
                │                                              │
                │            ┌──────────────────────────────────┘
                ▼            ▼
           │ balance │──> │ approve │──> │ execute │──FILLED──> │ settle │──> │ commit │
           │ слот,    │    │allowance│    │ submit/ │            │ зачисление│   │ фиксация │
           │ списание │    │ роутеру │    │ poll    │──SUBMITTED─┐│ unwrap  │   │ атомарно │
           │ wrap     │    │ ровно на│    └─────────┘            ││ сброс   │   │ trade.*  │
           └─────────┘    │ вход    │       │  ▲ поллинг         ▼│allowance│   └─────────┘
                          └─────────┘       │  └── retry_at ──┐  ▼└─────────┘
                             ▲               │   (PENDING)     │ │ FAILED на любом шаге:
                             └───────────────┼─────────────────┘ │ откат слота целиком,
                                   backoff   │  (retryable-отказ)  │ trade.failed,
                                             └─────────────────────┘ балансы целы
```

- **preflight** — валидация ордера и риск-лимиты (хопы, нотациональный
  лимит, allowlist тóкенов, согласованность маршрута и ордера);
- **ratelimit / breaker** — ГОТЫЕ шаги-шлюзы Universal API Runtime:
  бюджет и здоровье бэкенда — как у источников данных;
- **quote** — ожидаемый выход; `amount_out_min == 0` → авто-минимум от
  политики проскальзывания (`max_slippage_bp`);
- **balance** — торговый слот: списание входа (или wrap нативного —
  и передача маршрутизатору целиком); на повторных прогонах цепочки
  видит открытый слот и НЕ списывает дважды;
- **approve** — allowance ровно на сумму входа (аналог `forceApprove`);
- **execute** — отправка/поллинг бэкенда: `FILLED` / `SUBMITTED`
  (PENDING: `trade.submitted` + повтор цепочки для поллинга) / `REJECTED`
  (retryable → backoff + полный повтор, иначе терминальный отказ);
- **settle** — зачисление выхода, unwrap нативного, сброс allowance в 0;
- **commit** — атомарная фиксация слота + запись `trade.executed`.

### Ключевые инварианты (проверены тестами)

1. **Атомарность**: любое FAILED → откат ВСЕХ мутаций балансов ордера
   (`test_exec` сверяет балансы до/после отказных сделок).
2. **Нативный актив — только через unwrap**: прямой кредит нативного в
   слот запрещён (`TB_EXEC_NOT_WRAPPED`) — аналог guard `receive()`.
3. **Wrapped не задерживается**: после нативного входа wrapped-остаток
   равен нулю (контракт не держит WETH).
4. **Allowance всегда возвращается в 0** после расчёта.
5. **Минимум зафиксирован при отправке**: поллинг PENDING не меняет
   котировку и минимальный выход ордера.

### Записи журнала (конверт-схема)

`trade.executed` (SUCCESS), `trade.submitted` (PENDING, с `retry`),
`trade.failed` / `trade.canceled` (ERROR) — payload соответствует схеме
конвертов: `source` = имя бэкенда, `operation` = `swap_exact_in`,
`request_id` = id события реестра, суммы — десятичными строками.
Строгий разбор этих записей `tb_envelope_parse` — часть `test_exec`.
Терминальные события дополнительно пишутся как `event.trace` (мост
`tb_ev_ledger_attach`) — с полным следом шагов.

```json
{"event_id":9,"ts_ms":1793530642649,"ts":"2026-11-01T10:57:22.649Z",
 "type":"trade.executed","uuid":"trade.executed:2","payload":
 {"schema_version":"1.0","source":"sim-dex",
  "operation":"swap_exact_in","status":"SUCCESS","request_id":2,
  "timestamp":1793530642649,"data":{"order":2,"token_in":"0xbb..bb",
  "token_out":"0xaa..aa","amount_in":"2000000000000000000",
  "amount_out_min":"1972149971354463490",
  "amount_out":"1962080127698657376",
  "quote":"1992070678135821708","hops":1,"attempt":5}}}
```

### Симулятор бэкенда

`tb_exec_sim_init` — детерминированный стендалон: «цены» выводятся из
`crc32c(адрес, seed)` в фиксированной точке 1e6 на отрезке [0.5, 1.5),
за хоп вычитается fee тира и ценовое влияние маршрута. Сценарии
заполнения (немедленное / PENDING с задержкой / отказ с кодом) задаются
таблицей и расходуются по кругу — как сценарии ответов в `bot_demo`.
**Цены и объёмы симулятора — иллюстративные, рыночных данных нет.**
Граница подмены — интерфейс `tb_exec_backend_t`: в итерации «живые
данные» сюда встаёт реальный DEX-адаптер (HTTP-транспорт + конверты),
конвейер не меняется.

## 9. Живые данные: транспорт, DEX-адаптер, фильтры 1–4, Decision Engine (v0.3)

Арбитраж моделируется честной математикой без магии: **цикл
WETH→TOKEN→WETH — один exact-input ордер** с многохоповым маршрутом,
нога 1 (покупка) на пуле биржи A, нога 2 (продажа) на пуле биржи B.
Обе ноги — один атомарный торговый слот: сделка стала невыгодной —
отмена, слот откатывается целиком, теряется только моделируемый газ.

**Транспорт** (`tb/net`): `tb_http_t` — vtable синхронного запроса;
вызывающие — воркеры пула потоков, продолжения — в цикл (паттерн
bot_demo). Реализация net: сокеты + TLS (вендоренный mbedTLS 3.6.4,
проверка сертификата по системному CA, `TB_CA_FILE` для override),
Content-Length/chunked/до-закрытия, усечение тела помечается;
`host_pinned` — соединение по IP с Host/SNI из url (обход глючного
локального DNS-резолвера, аналог curl --resolve). Реализация replay —
детерминированные ответы по кругу для тестов. Коды `TB_NET_*`.

**DEX-адаптер** (`tb_dex`, `src/exec/backend_dex.c`): котировка маршрута
по хопам — `eth_call` к QuoterV2 (селектор `0xc6a5026a`, ABI-слова
собираются вручную — библиотек не нужно); комиссии пула и ценовое
влияние уже внутри чисел Quoter. Пул хопа берётся из `tb_route_pools`
(аддитивное поле v0.3) и приписан бирже в конфигурации (venue: RPC +
quoter + пулы). Исполнение — **shadow**: submit — свежая перекотировка
и сличение `min_out` (реверт-семантика роутера), сессия с модельной
задержкой; poll — заполнение по цене submit-котировки. Деньги
виртуальные; подпись транзакций (secp256k1, газ, nonce) — следующая
итерация. Маппинг ошибок: транспорт/429/5xx → `TB_EXEC_BACKEND`
(retryable, Retry-After проходит), revert/пустой result →
`TB_EXEC_INSUFFICIENT_LIQUIDITY`.

**Фильтры 1–4 и Decision Engine** (`tb_user`, чистые функции с
инъекцией котировщика): актуальность (возраст снапшота), ликвидность
(расхождение ставок probe и probe×mult — ценовое влияние в б.п.),
безопасность (биржа в allowlist топ-N), волатильность (отклонение
мидов истории от среднего). Решение: `profit(size) =
sell(buy(size)) − size − gas − min_profit`; поиск **минимальной
выгодной ставки** удвоением от минималки с бинарным уточнением,
потолок — **верх контракта** (`max_trade_wei`); если и на верхе
прибыли нет — сделка не предлагается (одна оценка на отсев).

**Рантайм** (`src/user/arb.c`): опрос пулов в воркерах (слоты
снапшотов фиксированы — гонок нет), фильтры и решение в воркере,
подача выгодных циклов — из потока цикла (`tb_exec_submit`);
монитор отмены держит PENDING-ордер под перекотировкой: продажа ниже
`min_out` — `tb_event_cancel` (откат слота, `decision.canceled`,
потерянный газ в статистике). Журнал: `decision.evaluated` —
**атрибуция влияния источников**: все котировки с возрастом, вердикты
каждого фильтра по каждому пулу, математика каждой пары; плюс
`decision.submitted` / `trade.*` / `event.trace`.

**Конфигурация** — JSON (`src/json/config.cpp`, C-ABI поверх
rapidjson): venues (RPC + quoter + пулы + host_pinned), watchlist
(токены/пулы/fee-тиры/биржа), пороги фильтров, decision-параметры.
Пример с реальными адресами Uniswap V3 mainnet —
`docs/arb_config.example.json`.

Демо: `arb_demo` (живой режим — реальные котировки; `--replay` —
локальный mock-RPC с синтетическим спредом ~0.7%, полный конвейер с
гарантированной сделкой). Тесты: `test_net`, `test_backend_dex`,
`test_filters`, `test_decision`, `test_config`.

## 10. Живое исполнение из Safe: кошельки и контракт средств (v0.4)

Модель кастодии — **Safe 1-из-2**: владелец-человек + горячий ключ
бота, порог 1. «Контракт на N эфира» = содержимое Safe: бот исполняет
свопы через `execTransaction` **изнутри** контракта — principal и
прибыль его не покидают; закрытие контракта = снять бота с владельцев
или вывести всё (прибыль остаётся в Safe). Компрометация ключа бота
теряет только содержимое Safe — это и есть риск-конверт.

**Жизненный цикл для пользователя** (всё на app.safe.global, бесплатно;
историю адреса смотрит и в Zerion/DeBank):
1. Создать Safe (сеть Ethereum), владельцы: свой кошелёк + адрес
   ключа бота (демо печатает его при старте), порог 1.
2. Пополнить контракт WETH на сумму «контракта».
3. Дать боту ключ (`TB_BOT_KEY` или `network.key_file`) и запустить
   `arb_demo --live-exec` (или `live_exec: true` в конфиге).
4. Закрытие: снять бота с владельцев / вывести средства из Safe.

**Технически** (`tb_sign`, `safe_exec`, live-режим `tb_dex`):
вендорены libsecp256k1 (подпись) и keccak-256 в ядре (селекторы,
хеши транзакций, EIP-712). Котировки прежние (QuoterV2); submit:
свежая котировка -> сличение минимума -> exactInput calldata
(path = маршрут как есть) -> SafeTx-хеш (EIP-712) -> подпись
ECDSA-владельца -> EIP-1559 -> `eth_sendRawTransaction`; poll:
receipt, фактический выход = **дельта balanceOf(Safe)** — истина с
цепи. Потолок газа `max_fee_wei`. Проверено против живого mainnet
RPC (chainId/газ/подпись) и полным циклом на mock-RPC
(test_safe_exec); отправка реальной транзакции — при запуске с
настоящим Safe (журнал trade.* несёт хеши).

## 11. Атрибуция: группы-владельцы, капсулы деталей, контракт контекста

Итерация «понять, кто не донёс» после отладки v0.3 (пустые «0x»-ответы,
ложные «арифметики», молчаливые ошибки котировщика в воркерах):

**Группы-владельцы** (`tb/core/ids.h`): замороженная решётка зон
ответственности (21 группа). Каждый .c объявляет `TB_CURRENT_GROUP`
первой строкой — макросы `TB_ERROR_SET/WRAP/PROMOTE` несут группу
файла, как `TB_LOC`; имя файла — документация, ид не зависит от
переименования. `tb_error_t.group` — «кто сообщил»; реестр кодов
несёт `owner` — канонического владельца (`tb_registry_ownership_check`
проверяет таблицу). Журнал: `event.trace`/`trade.failed` содержат
`"group":"dex"`; формат: `[USER:dex/TB_EXEC_SLIPPAGE|...]`.

**Капсулы деталей** (`tb/core/detail.h`) — кнопка «подробнее»:
компактные сырые данные на ошибке (кольцо из 2 слотов), команды
`NET_RAW` (статус+тело ответа), `DEX_HOP` (адрес+calldata+result),
`DECIDE_CURVE` (точки кривой поиска). `set` очищает, `wrap` хранит,
`promote` наследует происхождение; разворачивание — только по
требованию (`tb_error_format_details`, журнал ERROR-записей). Слепая
зона «0x от Quoter» видна без ручных принтов.

**Контракт контекста** (`tb/events`): событие несёт `ctx_has`
(битовые ключи `TB_CTX_*` «что донесено»), шаг объявляет требования
(`tb_evreg_add_needs`); прогон шага без нужных ключей — `TB_EV_CONTRACT`
с именем шага и маской недостающего. Реальная проводка: `preflight`
даёт `ORDER|ROUTE`, `quote` требует; снапшот рынка несёт `complete`
(все котировки донесены) — неполный отсекается фильтрами причиной
«контекст: снапшот неполный», а не ложной «аргументикой».

Тесты: `test_ids`, `test_details`, `test_ctx`. Это дополнение к
существующей обработке, не замена: ручные проверки и границы
инвариантов остаются.

## Контракты и ограничения

- **Потоковая модель**: один поток-владелец цикла (создавший — он же
  запускает); пул — для блокирующих операций; мьютекс только у входящей
  очереди постингов. Реестр событий однопоточный аналогично (мутации
  цепочки — из потока-владельца или до старта). Движок исполнения живёт
  в том же контракте: submit/destroy — из потока-владельца, как и всё.
- **Владение**: задача владеет `arg` через `dtor` (вызывается ровно один
  раз — после исполнения или при сбросе); `tb_error_t` — POD без владения;
  событие хранит ошибку по значению, след — текстом. Слот принадлежит
  ордеру: commit/rollback освобождают его ровно один раз; контекст ордера
  живёт до терминала события и убирается терминальным наблюдателем.
- **Отмена**: пометка `canceled`; освобождение при выборке из контейнеров.
  O(1)-удаление из куч/колеса — в роадмапе (сейчас задача живёт до слота).
  Событие отменяется из QUEUED/BLOCKED (`tb_event_cancel`), но не из ACTIVE.
  Отменённый ордер откатывает слот и пишет `trade.canceled`.
- **Ledger**: однопроцессный; восстановление пропущенных событий после
  простоя (повторные события, реорганизации блоков, дедупликация
  транзакций) — роадмап итерации устойчивости.
- **Envelope**: `data` — только JSON-объект или null (согласовано со схемой
  ответов источников).
- **Execution Engine**: с v0.3 бэкенд двоякий — симулятор (тесты) и
  живой DEX-адаптер (раздел 9): котировки настоящие, исполнение shadow
  на виртуальных балансах. Кошелёк —
  виртуальные балансы одного трейдера (основа 5B), multi-трейдерных
  счетов пока нет. Allowance ведётся на единственного «маршрутизатора»
  (spender один). PENDING-поллинг — повторами цепочки: каждый опрос
  проходит шлюзы (это осознанно — опрос = обращение к бэкенду).

## Роадмап следующих итераций

Адаптирован под реальность v0.2: механизм торговли уже стоит на реестре
событий и каркасе Universal API Runtime, поэтому фильтры 1–4 и движок
решений встраиваются в ГОТОВЫЕ цепочки, а не строятся заново.

1. **Итерация 3 — живые данные (ВЫПОЛНЕНА в v0.3)**: HTTP-транспорт (epoll-сокеты в цикле +
   пул), адаптер DefiLlama (без ключа) поверх реестра событий и конвертов;
   кэш ответов как шаг цепочки; конфигурация поставщиков (лимиты, backoff,
   breaker) из файла. Тот же транспорт закрывает и потребности исполнения:
   DEX-адаптер за интерфейсом `tb_exec_backend_t` заменяет симулятор,
   конвейер не меняется.
2. **Итерация 4 — устойчивость**: восстановление истории после простоя,
   обработка повторных событий, дедупликация транзакций по хешам;
   персистентность live-таблицы реестра и снимок кошелька на остановке
   (пережить перезапуск с открытыми PENDING-ордерами).
3. **Итерация 5 — модули 1–4 (фильтры)**: актуальность, ликвидность,
   безопасность, волатильность — как шаги цепочки событий домена USER
   (тот же реестр, тот же стиль шагов, что у исполнения); Decision Engine —
   агрегирующий шаг, чей выход — ордер в `tb_exec_submit`; Event Ledger —
   общий журнал решений и сделок.
4. **Итерация 6 — модуль 5**: 5A Decision/Shadow Evaluation — теневые
   сделки идут через ТОТ ЖЕ конвейер исполнения на виртуальных балансах
   (уже есть); 5B Strategy Research (Trade Slot Engine, архив котировок) —
   поверх записей `trade.*` и архива данных.
5. **Выделение `Universal API Runtime`** в отдельную переиспользуемую
   библиотеку проекта (envelope + backoff + rate limiter + breaker + кэш +
   реестр событий); `tb_exec` остаётся доменным слоем поверх неё.

## Числа демо — иллюстративные

Все ответы поставщиков в `bot_demo` симулированы сценариями; цифры в
`data`-payload не являются рыночными данными. Цены и объёмы симулятора
DEX в `exec_demo` — синтетические константы из хеша адресов; итоговые
балансы демонстрируют работу конвейера, а не доходность стратегий.
