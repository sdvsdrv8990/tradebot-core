# План v3 — дорожка к живой сделке (открыт 2026-11-03)

v2 закрыт полностью (кроме UI-оценки, ждёт браузера): математика
решения живая (газ с цепи, безубыточность + оптимум, глобальный поиск
по всем интервалам), исполнение propose-only и безключевое (Safe
1-из-1), дисциплина nonce/allowance, очередь Safe UI, market CLI,
параллельная решающая фаза, честный replay, CI gcc+clang+ubsan (29).

Всё это ещё не сделало ГЛАВНОГО: ни один человек не подписал ни одного
предложения на настоящем Safe. v3 = закрыть это и подтянуть то, что
встанет сразу после первой подписи.

## R1 — целостность маршрута и честный settlement (из ревью H1; ВЫПОЛНЕН)

Ревью владельца PR #11 вскрыло: «соответствует ли исполнение тем
пулам, по которым считалась прибыль?» — и ответ был НЕТ для кросс-DEX:
exactInput path не несёт адресов пулов, SwapRouter02 резолвит их
СВОЕЙ фабрикой (Uniswap) — ноги на Pancake исполнялись бы чужими
пулами или ревертились. Кросс-биржевая прибыль считалась по одним
пулам, исполнялась бы по другим.

Исправлено в PR #11 (доп. коммиты):
- гейт фабрики: предложение строится ТОЛЬКО если фабрика venue каждой
  ноги совпадает с фабрикой роутера исполнения (cfg.router_factory,
  дефолт Uniswap V3 mainnet); несовпадение — явный отказ; кросс-DEX
  закрыт до Multicall3 (пакет R2 ниже);
- атрибуция: три несмешиваемых состояния FOUND / ABSENT / ERROR
  (RPC не ответил — не «нет события»); колбэк on_execution вызывается
  ВСЕГДА; журнал: safe.executed / safe.rejected / safe.unattributed /
  safe.attribution_error — взаимоисключающие;
- дубль кода: SEARCH_INCOMPLETE = 19 (18 занят BAD_DECIMALS);
- getLogs от блока рождения предложения (born_block в submit);
- incomplete-поиск: подача маркируется "preliminary": true (прибыль
  реальна и защищена min_out, оптимальность объёма не доказана);
- stop-storm: 12 таймингов.

Тесты из разбора (примеры владельца — в приёмку):
- уникальность всех кодов TB_EXEC явной проверкой пар (enum C молчит
  при дубле значений — как с двумя 18-ми);
- неполный поиск: кривая с пятью окнами съедает бюджет проб ->
  incomplete=true, «невыгодно» запрещено, размер/минимум валидны;
- getLogs от born_block: мок захватывает fromBlock запроса,
  равен блоку рождения (не «текущий-4096»);
- гейт фабрики КАЖДОГО хопа: двухногочный маршрут, вторая нога
  чужой фабрики — предложение не строится (первая «своя» не спасает).

## R2 — MultiSendCallOnly: кросс-DEX атомарно (офлайн-часть ВЫПОЛНЕНА)

Замечание: не Multicall3 (агрегатор тянет токены transferFrom-ом от
msg.sender — им был бы сам агрегатор), а MultiSendCallOnly: Safe
execTransaction -> MultiSend.multiSend(bytes) — внутренние вызовы
идут ОТ Safe (msg.sender = Safe, transferFrom роутеров работает),
одна транзакция, отказ ноги ревертит всё.

Реализовано (офлайн, без живой транзакции):
- сегментация хопов по роутерам: фабрика роутера -> safe.router
  (прямой путь), чужая фабрика -> venue.router своей биржи; хоп без
  роутера — явный отказ;
- пачка MultiSendCallOnly (канонический адрес, tb_safe_code_exists
  для проверки на цепи при live-старте);
- цепочка минимумов: последний сегмент — пол ордера; промежуточные —
  ожидаемый выход × (final_min/final_expected + 1 б.п.) — та самая
  двухуровневая защита из исходного аудита;
- тест 6m: декод пачки (селектор multiSend(bytes) сверен keccak),
  2 вызова, каждая нога своим роутером, path-тиры на месте,
  финальный минимум == order min_out, промежуточный строго между
  0 и ожиданием; eth_sendRawTransaction по-прежнему 0 вызовов;
- stop-storm v2: детерминированная остановка посреди оценщиков
  (TB_ARB_TEST_STOP_MID — сворачивает конвейер, цикл жив: done-ы
  доходят до комбинера), журнал обязан содержать decision.evaluated
  (= все воркеры дренажились) + чистый выход.

Живая часть (в чек-лист L1): реальная MultiSend-транзакция в Safe UI,
реверт-поведение на цепи, getCode-проверка адреса при live-старте,
approve обоим роутерам.

## R3 — правки ревью R2/F1/L2 (ВЫПОЛНЕН)

Из разбора владельца PR #14/#15/#16:
- seg_scale: u128-произведение могло переполниться ДО проверки, а
  отказ молча ставил промежуточный минимум 1 wei — защита почти ноль.
  Теперь честная u256-арифметика (разложение по словам); невозможность
  посчитать = ОТКАЗ строить предложение (не ослабление); попутно
  поймана потерянная строка деления (ratio x10000). Тест 6n: суммы
  1e21 (вне u64) — корректный минимум или явный отказ;
- ворота F1: GATE_VALID / GATE_REFRESHING / GATE_FAILED — при начале
  пересчёта старый профиль перестаёт действовать; сбой RPC не
  оставляет вердикт «по инерции»; возраст по wall-clock тоже;
- streaks L2: LRU-вытеснение по last_poll (заполненная таблица прежде
  молча блокировала дозревание новых пар);
- Telegram-хук on_propose_cmd — опционален (решение владельца:
  вероятно не нужен, Safe сам доставляет); /proposals —
  диагностическая страница, «пусть живёт», уберём после L1.

## L1 — живая репетиция (первый приоритет)

Цель: первая в истории проекта подписанная человеком транзакция по
предложению бота — approve, затем своп на пыли WETH — и сквозной
settlement в журнале. Это операционный пакет: код, скорее всего, уже
готов; всплывут швы — чиним по факту.

Чек-лист (runbook в README, отдельная секция):
1. Safe 1-из-1 создан (владелец — кошелёк человека), пополнен пылью
   WETH (~0.01) — риск-конверт первой live-сделки равен пыли;
2. `arb_config.json`: safe/router/live_exec=true; сервис очереди вкл;
3. запуск `./run.sh`: бот читает цепь, allowance-гейт предлагает
   approve (файл proposals/ + очередь app.safe.global);
4. человек: проверяет параметры в Safe UI (verify-блок — числа),
   подписывает approve, затем первую сделку;
5. бот: рост nonce → дельта баланса → trade.executed в журнал;
   ни одной транзакции от бота (это проверяет и CI, и журнал);
6. на репетиции замерить: сколько минут занимает подпись (цифра для
   буфера L2); сколько предложений потеряло прибыль до подписи;
7. проверить публикацию без подписи автора: Safe TX Service может
   требовать подпись Proposer-а (не владельца!) — если безключевой
   POST отклонится: включить бота Proposer-ом в настройках Safe
   (без права подписи) или добавлять предложения через Transaction
   Builder UI. Живая проба — единственный способ узнать.

Приёмка: в журнале есть цепочка safe.queued → (подпись человеком) →
исполнение с фактической дельтой; человек подтвердил, что параметры в
кошельке совпали с verify-блоком артефакта.

## L2 — экономика предложений под человеческую скорость

Окно арбитража живёт секунды, подпись — минуты; без доработки почти
каждое предложение истечёт честно. Пакет:
- персистентность: пара допускается к предложению только после
  K подряд батчей со спредом (выжила 2-3 опроса — вероятнее проживёт
  минуты); K — константа дисциплины, не ручка прибыльности;
- переоценка спреда прямо перед предложением (сейчас оценка на блоке
  батча — достаточно, зафиксировать тестом);
- буфер исполнения: 5 б.п. рассчитаны на секунды — для live-предложений
  поднять до величины, честной относительно времени подписи (решение
  владельца по цифре после L1: сколько минут человек реально подписывает);
- статистика предложений в журнал/морду: подано / исполнено / истекло /
  заменено — по этим чисрам L2 калибруется.

## L3 — человек должен узнать (уведомление)

Пока предложение живёт в консоли/файле/очереди — человек должен быть у
монитора. Минимально без новых зависимостей:
- `network.on_propose_cmd` в конфиге: команда, исполняемая при каждом
  предложении (аргументы — путь артефакта, kind, nonce); владелец
  вешает свой telegram-скрипт/звонок сам;
- страница «Предложения» в морде: таблица живых/последних предложений
  (kind, пара, размер, min_out, nonce, истекает) — данные уже есть в
  журнале, нужен только вывод.

## L5 — отчётность после первых сделок

`market report`: чтение журналов, сводка по парам/биржам — PnL,
исполнено/истекло/заменено, газ. Появляется смысл только после L1.

## L4 — глубже рынок (опционально, решение владельца)

Треугольные маршруты WETH→A→B→WETH: больше возможностей, но и больше
RPC; параллельная решающая фаза уже готова это тащить. В v3 — только
если L1-L3 закрыты быстро и есть аппетит.

## Бэклог

- stop-storm v2: управляемые точки синхронизации вместо таймингов
  (гарантия попадания в решающую фазу) + проверка завершения всех
  воркеров (ревью H1); текущие 12 таймингов — рабочий минимум;
- UI-оценка «≈ спред-оценка» → реальная котировка на объёме (ждёт
  браузер для проверки морды);
- Arbitrum: адреса разведаны в v1 (quoter/factory живые) — подключение
  чисто конфигом при желании;
- keep-alive транспорта: снизит TLS-рукопожатия, станет заметно при
  росте пула наблюдения.
