# План v3 — дорожка к живой сделке (открыт 2026-11-03)

v2 закрыт полностью (кроме UI-оценки, ждёт браузера): математика
решения живая (газ с цепи, безубыточность + оптимум, глобальный поиск
по всем интервалам), исполнение propose-only и безключевое (Safe
1-из-1), дисциплина nonce/allowance, очередь Safe UI, market CLI,
параллельная решающая фаза, честный replay, CI gcc+clang+ubsan (29).

Всё это ещё не сделало ГЛАВНОГО: ни один человек не подписал ни одного
предложения на настоящем Safe. v3 = закрыть это и подтянуть то, что
встанет сразу после первой подписи.

## Принятые модели (перенесены из v2, не пересматриваем)

1. Propose-only, без ключа: бот никогда не отправляет транзакции.
2. Истина — цепь: nonce(Safe) + дельта balanceOf.
3. Конфиг — данные: market CLI, ячейки, снапшоты, откат.
4. Один план — короткий: детали в README/ARCHITECTURE и PR.

## L1 — живая репетиция (первый приоритет)

Цель: первая в истории проекта подписанная человеком транзакция по
предложению бота — approve, затем своп на пыли WETH — и сквозной
settlement в журнале. Это операционный пакет: код, скорее всего, уже
готов; всплывут швы — чиним по факту.

Чек-лист (runbook в README, отдельная секция):
1. Safe 1-из-1 создан (владелец — кошелёк человека), пополнен пылью
   WETH (~0.01) — риск-конверт первой live-сделки равен пыли;
2. `arb_config.json`: safe/router/live_exec=true; сервис очереди вкл;
3. запуск `./run.sh`: бот читает цепь, allowance-гейт предлагает
   approve (файл proposals/ + очередь app.safe.global);
4. человек: проверяет параметры в Safe UI (verify-блок — числа),
   подписывает approve, затем первую сделку;
5. бот: рост nonce → дельта баланса → trade.executed в журнал;
   ни одной транзакции от бота (это проверяет и CI, и журнал).

Приёмка: в журнале есть цепочка safe.queued → (подпись человеком) →
исполнение с фактической дельтой; человек подтвердил, что параметры в
кошельке совпали с verify-блоком артефакта.

## L2 — экономика предложений под человеческую скорость

Окно арбитража живёт секунды, подпись — минуты; без доработки почти
каждое предложение истечёт честно. Пакет:
- персистентность: пара допускается к предложению только после
  K подряд батчей со спредом (выжила 2-3 опроса — вероятнее проживёт
  минуты); K — константа дисциплины, не ручка прибыльности;
- переоценка спреда прямо перед предложением (сейчас оценка на блоке
  батча — достаточно, зафиксировать тестом);
- буфер исполнения: 5 б.п. рассчитаны на секунды — для live-предложений
  поднять до величины, честной относительно времени подписи; ЦИФРА —
  из замера на L1 (сколько минут реально занимает подпись человека),
  не из предположений;
- статистика предложений в журнал/морду: подано / исполнено / истекло /
  заменено — по этим чисрам L2 калибруется.

Разделение данных для теста (решение владельца): адреса/ABI/селекторы/
форматы событий — из доков, сверяются на месте (keccak, getLogs),
БЕЗ хардкода; поведение живой очереди (задержка появления предложения,
профиль 429/Retry-After, фактическое время подписи, отставание
индексера) — только от реального контракта на L1. О проблемах второго
рода нельзя судить без реальной работы — L1 их источник.

## F1 — горячий контур (скорость принятия решений)

Решение владельца: все 4 фильтра — тоже события, влияющие на
планировщик; на стабильных парах их картина меняется редко (даже в
штормы), а главное в бою — скорость решения. Значит: информацию от
фильтров собирать на СТАРТЕ торговли, дальше — следить только за
ценами в реальном времени; лишние фильтры в горячем пути неуместны.

Замер по коду: сейчас каждый опрос = 3 котировки на пул (probe,
большая проба ликвидности, круг sell_back) — 30 пулов = 90 RPC на
батч только снапшотов. Для спреда и решения нужна одна (probe).

- старт (каданс ворот, затем медленная страховка раз в G опросов):
  полный профиль пула — большая проба (impact), круг (round_bp),
  история волатильности, вердикт всех 4 фильтров → событие ворот
  планировщику: пул допущен/отведён к горячему контуру;
- горячий контур (каждый опрос): ТОЛЬКО probe-котировка (1 eth_call
  на пул) + номер блока; freshness — арифметика; спреды из probe;
  решающая фаза без изменений (свои котировки, кеш, бюджет);
- safety-allowlist — предвычисленная таблица на старте (сейчас strcmp
  на каждый снапшот каждый опрос);
- эффект: снапшотные RPC 3/пул -> 1/пул (−66%), батч втрое ближе к
  блоку — либо тот же бюджет оборачивается чаще опросом;
- честность: осушение пула между кадансами ворот ловит решающая фаза
  (плохие котировки/отказ уже атрибутируются: quote_errors /
  SEARCH_INCOMPLETE); G — константа дисциплины (вариант владельца
  «строго старт, без каданса» тоже допустим — решает L1-опыт);
- морда: impact/round_bp — «последнее известное с кадров ворот» с
  меткой времени каданса.

## L3 — события → планировщик; человек должен узнать

Архитектурный принцип (решение владельца): НЕ привязываться к подпискам
(вебхуки/подписки сервисов, платные тарифы уведомлений) — это бред как
основа. Внешние события (ответы Safe TX Service: очередь/429/статус,
события цепи) принимает ОБРАБОТЧИК, который лишь адекватно их
разбирает и передаёт ПЛАНИРОВЩИКУ (tb_loop) — он уже управляет всеми
процессами и решает, что делать: уведомить, перечитать allowance,
пометить предложение исполненным. Сервисы остаются отключаемым
каналом доставки, не источником управления.

- `network.on_propose_cmd` в конфиге: команда при каждом предложении
  (аргументы — путь артефакта, kind, nonce); владелец вешает свой
  telegram-скрипт/звонок сам — минимальный ручной крючок;
- обработчик сервисных событий: ответы очереди (успех/429/статус)
  становятся событиями планировщика (счётчики и решения уже есть:
  service_rate_limited, safe.queued, атрибуция) — уведомления
  производны от них, а не от подписки;
- страница «Предложения» в морде: таблица живых/последних предложений
  (kind, пара, размер, min_out, nonce, истекает) — данные уже есть в
  журнале, нужен только вывод.

## L5 — отчётность после первых сделок

`market report`: чтение журналов, сводка по парам/биржам — PnL,
исполнено/истекло/заменено, газ. Появляется смысл только после L1.

## L4 — глубже рынок и торговая сессия (опционально, решение владельца)

Расширение от владельца: колебания курсов — главный источник работы;
цена (биткоин-пример) меняется часто, стоимость транзакции — гораздо
реже; отсюда две опоры, обе уже в коде:
- ОТМЕНА сделки — критический механизм межбиржевой торговли (снизить
  потери, если этап стал невыгодным): монитор отмены перекотирует
  каждый PENDING-ордер и гасит его ниже минусов безубыточности
  (decision.canceled; в propose-модели — замена/истечение живого
  предложения). Остается критичной при любом расширении;
- минимальные суммы с учётом комиссии: движок ищет точку
  безубыточности и оптимум, потолок — абсолютный лимит капитала.

Новые цели пакета (расширение, «почти всё для этого есть»):
1. только активы, которые поддерживает кошелёк — с Safe это любой
   ERC-20; кошельки умеют добавлять валюты до листинга на бирже —
   это возможность раннего входа (рынок тоньше, спреды шире);
   фильтр допуска = лист активов конфига (market asset …), уже есть;
2. ЦЕЛЬ СЕССИИ: каждая торговая сессия обязана закончиться в ИСХОДНОЙ
   валюте — прибыль можно снять. Сегодня цикл атомарен
   (WETH->TOKEN->WETH) — цель выполняется на каждой сделке; расширение
   — треугольные маршруты WETH->A->B->WETH (больше возможностей при
   тех же RPC-бюджетах; параллельная решающая фаза готова) и сессии
   с позициями: журнал сессии считает PnL в базовой валюте, конец
   сессии — конвертация остатков в базу (бот предлагает финальные
   сделки), после чего прибыль снимается.
Приёмка: ни одна сделка/сессия не оставляет «висящих» остатков в
не-базовой валюте без явного предложения конвертации; PnL сессии в
журнале сходится с дельтой баланса Safe.
