# tradebot-core — ядро торгового бота

Ядро децентрализованной арбитражной торговли на C11/C++20 (Linux):
событийный планировщик, реестр событий с цепочками шагов, Event Ledger,
конвейер исполнения с атомарными слотами, живые котировки Uniswap V3
(QuoterV2 через публичный RPC) и живое исполнение из Safe
(EIP-1559, EIP-712). Фильтры 1–4 + Decision Engine: две фазы на паре
пулов — точка безубыточности и оптимальный объём максимума чистой
прибыли (газ — живой с цепи, порог = минимум + буфер риска от размера).

Подробности устройства — в [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md).

## Разработка: веточный флоу (fork flow)

Работа идёт ветками, в `main` попадает только проверенное через PR:

1. **Ветка под задачу** — от свежего `main`:
   `git checkout main && git pull && git checkout -b <тема>-<суть>`
   Имена: `p0-safe-approve`, `p2-ui-pairs`, `fix/…` — коротко и по делу.
2. **Коммиты тематические** — один логический шаг = один коммит,
   сообщение в стиле `тема: что сделано` (+ тело с деталями при необходимости).
   Тесты и сборка зелёные ДО коммита: `ctest --test-dir .build`.
3. **Push и PR**:
   `git push -u origin <ветка>`, затем PR в `main`
   (веб-интерфейс или `gh pr create`).
4. **Ревью и мерж**: squash-merge — в истории `main` одна запись на
   задачу; ветку после мержа удаляем (кнопка в PR / `git push origin :<ветка>`).
5. **Чужие репозитории** — тот же путь через форк: fork → ветка в
   форке → push в форк → PR upstream.

`main` всегда собирается и проходит тесты; live-изменения (деньги,
подписание) — только через PR с явным ревью.

## Развёртывание и запуск

Одна команда из корневого каталога: при необходимости собирает
(зависимости локально в `.deps/`, без root) и поднимает бота вместе с
веб-мордой. Привязки ко времени нет — работает до остановки.

Установка

```bash
./setup.sh all           
```

Запуск

```bash
./run.sh addr     # адрес ключа бота — его добавляешь владельцем в Safe
./run.sh          # бой: бот + веб-морда http://127.0.0.1:8080
./run.sh stop     # остановка (Ctrl+C / kill тоже работают)
```

### Веб-морда: страницы-микромодули

Страницы — подключаемые модули: какие подняты, порт и период обновления
задаются в конфиге (`web`), данные морда берёт из единых источников
(снапшоты цикла под мьютексом, журнал — read-only fd), бизнес-логика
не затрагивается.

- **Дашборд** `/` — карточки состояния + последние решения/сделки;
- **Биржи и цены** `/venues` — наблюдаемые биржи и пулы (блок и свежесть
  у каждого), спреды пар (только свежие снапшоты одного блока), колонка
  «≈ спред-оценка» — оценка probe×спред; карточка сверху — **реальная
  котировка** лучшей пары (маршрут WETH→TOKEN→WETH через обе биржи,
  честный минус тоже честно);
- **Сделки** `/trades` — все сделки: статус, вход/выход ETH, профит,
  ошибки с атрибуцией (etherscan-стиль).

```json
"web": {"port": 8080, "refresh_ms": 2000,
        "pages": ["dashboard", "venues", "trades"]}
```

Новая страница = один `tb_web_page_t` (путь, заголовок, JS) в таблице
регистрации + строка в конфиге.

Морда поднимается **до** стартерных проверек цепи и отвечает сразу
(данные — после первого решённого батча). Кому слушать — поле `bind`:
`"127.0.0.1"` (по умолчанию, только локально) или `"0.0.0.0"` (все
интерфейсы — открывать с другой машины; морда read-only, но историю
сделок видно всей сети, держите сервер за NAT/файрволом).

### Биржи и пары (конфиг)

Межбиржевой арбитраж: одна и та же WETH-пара покупается на одной бирже
и продаётся на другой, заработок — разница курсов. В примере конфига —
**четыре биржи** Ethereum mainnet и 23 пула по топ-10 ERC-20:

- **uniswap-v3** (12 пулов): USDC 0.05/0.3%, USDT 0.05%, DAI 0.01/0.05%,
  WBTC 0.05%, LINK 0.05%, UNI 0.05%, SHIB 0.3%, PEPE 0.3%, AAVE 0.05%,
  LDO 0.3%;
- **pancakeswap-v3** (5 пулов): USDC 0.05%, USDT 0.05%, WBTC 0.05%,
  UNI 1%, PEPE 1%;
- **sushiswap-v2** (4 пары): USDT, USDC, DAI, WBTC (комиссия 0.30%);
- **uniswap-v2** (2 пары): USDC, USDT (комиссия 0.30%).

Кросс-биржевые пары: USDC (4 пула!), USDT (3), WBTC (3), DAI, UNI, PEPE;
остальные токены торгуются между fee-тирами своей биржи.

**Мультичейн**: у venue поля `chain_id` и `weth` (нет — цепь
network.chain_id, хаб общий). В примере добавлена Base (8453):
uniswap-v3-base и pancakeswap-v3-base, 7 пулов USDC/USDbC/DAI —
кросс-биржевые пары ВНУТРИ Base. Каждая цепь котируется на СВОЁМ
блоке (номер блока чужой цепи не существует), пары сравниваются
только в пределах цепи; страница показывает цепь каждого пула.

Два метода котировки за одним `tb_exec_backend_t` (конвейер не меняется):

- **V3** (`"type": "v3"`, по умолчанию): `QuoterV2.quoteExactInputSingle`
  — поля `quoter` + `factory`;
- **V2** (`"type": "v2"`): `Router.getAmountsOut` — поля `router` +
  `factory` (для проверки `getPair`); комиссия 0.30% уже внутри
  котировки, поэтому у V2-пулов в конфиге `fee: 3000` — валидатор
  требует именно это значение.

Схема конфига — реестр (В9): `rpc[]` описывает только биржи, а каждый
пул в `pools[]` ссылается на свою биржу полем `dex` — загрузчик сам
приписывает пулы биржам, двойного объявления (`rpc[].pools`) больше
нет, рассинхрон невозможен по построению. Новая биржа/пул = только
конфиг (`rpc[]` += venue, `pools[]` += запись с `dex`). При старте бот:

1. **Валидирует конфиг** (fail-fast до сети): имя `dex` объявлено в
   `rpc[]`, пул приписан именно этой бирже, дублей адресов нет; у V2
   fee = 3000; у V2 задан router, у V3 — quoter;
2. **Проверяет пулы на цепи**: V3 — `Factory.getPool(weth, token, fee)`,
   V2 — `Factory.getPair(weth, token)`; адрес с цепи обязан совпасть
   с конфигом (фабрика — истина, докам не верим);
3. **Читает symbol/decimals токенов с цепи** (кэш; страница показывает
   символы, а не адреса);
4. Котирует каждый батч **на одном блоке** (`eth_blockNumber` → все
   `eth_call` батча с этим номером): сравниваются цены одного состояния
   цепи, пары из разных блоков не сравниваются.

Адреса фабрик/Quoter'ов/роутеров в примере подтверждены на цепи живыми
котировками (у зеркала mainnet адрес фабрики Uniswap V3 отличается от
доков — проверка на старте ловит именно такие расхождения).

Период опроса 15 с и свежесть 45 с в примере честные: транспорт без
keep-alive делает TLS-рукопожатие на каждый запрос, батч 23 пулов —
это ~70 RPC.

### Математика решения (без ручных порогов прибыльности)

Решение по паре пулов считается из рыночных данных, а не из настроек:

- **газ цикла** = цена газа с цепи на момент батча (`eth_gasPrice` +
  приоритетная премия) × константа формы транзакции `TB_ARB_GAS_UNITS`
  (420k газа: Safe `execTransaction` + `exactInput` двух хопов).
  `decision.gas_est_wei` — только фолбэк, когда RPC не ответил;
- **требуемая прибыль** = `min_profit_wei` (абсолютный защитный
  минимум) + 5 б.п. от размера (буфер движения цены между расчётом и
  включением в блок) — масштабируется вместе со ставкой;
- **точка безубыточности** — минимальный размер с нулевой чистой
  прибылью: движок ищет её сам от пола 1e-6 ETH (`min_trade_wei` в
  конфиге больше не обязателен; ненулевое значение — ручной пол);
- **оптимальный объём** — максимум чистой прибыли: удвоение от точки
  безубыточности до первого спада, затем тернарное уточнение пика.
  Ордер подаётся именно на оптимальный объём; `min_out` ордера =
  оптимальный объём + газ + требуемая прибыль (пониже — реверт роутера).

`profit(size) = sell(buy(size)) − size − газ − требуемая прибыль`, где
котировки — точные eth_call QuoterV2 (комиссии и влияние размера уже
внутри чисел). `max_trade_wei` остаётся абсолютным потолком капитала
на сделку, `max_fee_wei` — потолком цены газа живой отправки.

### Боевой запуск (live): бот готовит — человек подписывает

Модель исполнения **propose-only**: бот НЕ отправляет транзакции и не
может потратить средства в одиночку. Он находит возможность, считает
объём и границы, готовит SafeTx (calldata с min_out, EIP-712-хеш,
свою подпись владельца) и отдаёт предложение: консоль + JSON-файл
`proposals/` + запись `safe.proposal.*` в журнал. Человек проверяет
параметры в кошельке и подписывает; после порога подписей транзакция
исполняется. Бот узнаёт об исполнении по росту nonce Safe, результат
считает дельтой `balanceOf` — истина с цепи, не наша котировка.

1. Ключ бота: `openssl rand -hex 32 > bot_key.hex`, затем
   `./run.sh addr` — адрес ключа (0x…).
2. Создать Safe на [app.safe.global](https://app.safe.global)
   (Ethereum): владельцы — **твой кошелёк и адрес бота, порог 2**.
   Ни одна транзакция не исполняется без твоей подписи — ключ бота
   лишь готовит предложения (компрометация ключа не тратит капитал).
3. Пополнить: **WETH на Safe** (торговый капитал). ETH на адресе ключа
   бота для газа НЕ нужен: бот ничего не отправляет.
4. `arb_config.json` (копия примера): `network.safe` = адрес Safe,
   `network.key_file` = `"bot_key.hex"`, `network.live_exec` = `true`.
   Абсолютные ограничители: `max_trade_wei` (потолок капитала на
   сделку), `min_profit_wei` (защитный минимум), `max_fee_wei`.
5. `./run.sh` — старт. Если allowance WETH→роутер ниже рабочего лимита
   (max_trade × 100), бот первым делом подготовит **предложение
   `approve`** — подпиши его в Safe UI; до этого свопы будут
   ревертиться на `transferFrom`.
6. Каждая найденная возможность = предложение `safe.proposal.trade`:
   проверь в кошельке декодированный `exactInput` (пул-маршрут,
   amountIn, **amountOutMinimum** — твой пол прибыли) и подпись.
   Исполняться через Safe UI; бот ждёт до 30 минут, затем снимает
   наблюдение (на цепи ничего не тратится).

Честные ограничения модели: окно арбитража живёт секунды, подпись
человеком — минуты; большинство предложений разумно не подписывать,
если момент ушёл (min_out отвергнет невыгодное исполнение — но газ
подписанной транзакции при реверте тратится). Контроль nonce — по
факту исполнения любой транзакции Safe: если в окно исполнилась чужая
(например, другой подписанный своп), расчёт закроется по общей дельте
баланса. Автономной отправки в коде больше нет вовсе
(`tb_safe_send_exec` удалён).

Демо подсистем (после сборки лежат в `.build/`):

| Демо | Что показывает |
|---|---|
| `arb_demo` | арбитражный конвейер: фильтры 1–4, Decision Engine (минимальная ставка до верха контракта) |
| `bot_demo` | опрос источников: 429/Retry-After, backoff+jitter, circuit breaker, Event Ledger |
| `events_demo` | реестр событий: цепочка шагов, загрузка/выгрузка на ходу, мосты к планировщику и журналу |
| `exec_demo` | механизм торговли: preflight→commit, атомарность слота, PENDING, slippage-защита |

## Структура проекта

```
tradebot-core/
├── run.sh                     # развёртывание: бот + веб-морда одной командой
├── setup.sh                   # стадии сборки: deps | build | test | всё
├── CMakeLists.txt / Makefile   # сборка (основная + запасной путь без CMake)
├── include/tb/                 # публичные заголовки (C-ABI)
│   ├── core/     #   error, registry, ids, detail, keccak, log, time, alloc
│   ├── sched/    #   task, pqueue, timer, loop, threadpool, backoff
│   ├── runtime/  #   ratelimit, breaker
│   ├── events/   #   events (реестр), builtins (шаги-шлюзы)
│   ├── ledger/   #   ledger (JSONL-журнал)
│   ├── exec/     #   codes, u256, route, wallet, backend, backend_dex,
│   │             #   safe_exec (живое исполнение из Safe), engine
│   ├── net/      #   http (транспорт net + TLS / replay)
│   ├── sign/     #   tx (ключ, RLP, EIP-1559)
│   ├── user/     #   arb (фильтры 1–4, Decision Engine, рантайм)
│   ├── json/     #   envelope, config (C++/rapidjson с C-ABI)
│   └── arch/     #   arch (asm-хот-споты)
├── src/            # реализация (зеркалит include/)
├── tests/          # 26 тестов
├── docs/           # ARCHITECTURE.md, образцы журналов, arb_config.example.json
└── third_party/    # rapidjson, mbedtls, secp256k1 (вендор)
```

Библиотеки: `tb_core` (C11), `tb_net` (HTTP/TLS), `tb_sign`
(EIP-1559), `tb_dex` (DEX-адаптер + Safe), `tb_user` (арбитраж),
`tb_runtime` (C++/rapidjson). Демо и тесты линкуются против них.
